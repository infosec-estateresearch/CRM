# CRM-007 — `crm-beta` environment, release bundle and clean-host verification

- **Version:** v1.0, 2026-11-10.
- **Authority:** the PO priority override of 2026-11-10 (Issue #9), § 5 "Secure beta environment". It retains PBI-016 (release packaging) and PBI-017 (clean-host verification), and organises them so they cause no extra delay.
- **Parent PBI:** CRM-PBI-011, PBI-016 and PBI-017.

## Outcome

A second, fully separate Compose project, `crm-beta`, that is built **only** from a verified release bundle. It runs on DOCKER1 next to `crm-dev` and shares nothing with it. It is reachable **only** through the PO's upstream HAProxy, which terminates TLS. It has:
- named users, enforced roles and audit (CRM-003);
- daily backups and a tested restore;
- root-only storage for customer data.

Deploying the bundle into an **empty** beta runtime **is** the clean-host verification (PBI-017).

## Facts verified by the PL on DOCKER1
- No HAProxy runs on DOCKER1. The PO's HAProxy is upstream.
- Docker uses the userland proxy, so containers that publish ports see every LAN client as the bridge gateway. Source filtering by Apache inside `crm-app` is therefore impossible.
- Host firewall tools are prohibited (PO standing rule).

## Change

1. **Parameterise the environments.**
   - Generalise the CRM-001 scripts (`up.sh`, `backup.sh`, `restore.sh`, `export.sh`, `deploy_custom.sh`, `lib/common.sh`, `check_access.py`) from the fixed `dev` target to `dev|beta`. Each target has a fixed runtime root (`/srv/CRM/runtime/dev` or `/srv/CRM/runtime/beta`) and Compose project (`crm-dev` or `crm-beta`). Both are constants, never derived from input.
   - All CRM-001 guards stay, for both targets.
   - `beta` additionally refuses:
     - synthetic seeding;
     - a runtime that isn't root `0700`;
     - any bind other than `127.0.0.1` for `crm-app`.
2. **Beta edge: `crm-beta-edge`.**
   - The edge proxy is a pinned `haproxy` LTS image, digest registered in `security/EXTERNAL_CODE_REGISTER.yaml`.
   - It runs with `network_mode: host` and binds **only** `${CRM_BETA_BIND_IP}:${CRM_BETA_PORT}`.
   - Because it runs on the host network, it sees real source addresses. It accepts connections **only** from `${CRM_BETA_UPSTREAM_SOURCES}` (the PO's HAProxy, at most a /32 list) and forwards to `crm-beta`'s `crm-app` on `127.0.0.1:${CRM_BETA_APP_PORT}`.
   - It sets `X-Forwarded-Proto: https` and the `X-Forwarded-For` it received, only for those trusted sources. It drops anything else with 403.
   - Hardening: read-only root filesystem, `cap_drop: ALL` plus only `NET_BIND_SERVICE` if the port is below 1024, non-root, `no-new-privileges`.
   - Its configuration is Git-controlled and validated fail-closed by `check_access.py beta`. The source list must be private /32s, and there must be no `0.0.0.0/0`.
   - EspoCRM `siteUrl` is `https://${CRM_BETA_HOSTNAME}`, set with `bin/command config:set siteUrl`.
3. **Release bundle (PBI-016).**
   - `scripts/release.sh <commit>` builds `crm-release-<shortsha>.tar.gz` from `git archive` of an **accepted** commit, plus a `RELEASE.json`.
   - `RELEASE.json` records the commit, the image digests (taken from the register), the sha256 of every file, and the CRM-002 to CRM-006 delivery-record commits.
   - The bundle is reproducible from the same commit, byte for byte.
4. **Clean-host deploy (PBI-017).** `scripts/deploy_release.sh beta <bundle>`:
   - verifies `RELEASE.json`;
   - refuses a non-empty beta runtime unless `--upgrade` is given;
   - unpacks into `/srv/CRM/deploy/<shortsha>`, root-owned and read-only;
   - creates the runtime;
   - deploys `custom/`;
   - provisions access (CRM-003);
   - runs the acceptance suite in **beta-safe mode**: read-only checks only, with no seeding and no synthetic writes;
   - writes a sanitised deploy report.
5. **Backups.**
   - `backup.sh beta` writes to `/srv/CRM/runtime/beta/backups` (root `0700`, files `0600`).
   - Provide a timer unit template under `deploy/beta/`, installed by the operator only with PO consent. Don't install it from scripts.
   - Retention follows `docs/MIGRATION-DATA-HANDLING.md`.
   - The restore test runs against a throwaway project, `crm-beta-restoretest`, that publishes nothing and is destroyed afterwards.
6. **Tests (unit, in-process):**
   - target guards for `dev|beta`;
   - the beta bind policy;
   - the edge config policy, with broken fixtures (`0.0.0.0/0`, missing source list, a forwarded header trusted from any source, binding on all interfaces);
   - bundle reproducibility and verification refusals (a tampered file, a wrong digest);
   - deploy refusing a non-empty runtime.

   Every CRM-001 to CRM-006 test still passes.
7. **Docs:**
   - `docs/BETA.md`: the architecture, the HAProxy upstream contract (what the PO configures upstream), operator steps, access control, backup and restore, and data handling;
   - `docs/RELEASE.md`.

## Scope

**Allowlist:**
- `scripts/**`, `deploy/**`, `tests/**`
- `security/EXTERNAL_CODE_REGISTER.yaml`
- `docs/BETA.md`, `docs/RELEASE.md`, `docs/BUILD.md`
- the README usage section
- `.forge/CRM-007/**`

**Excluded:**
- `custom/` (except deploying it);
- `migrate/` and `load/`;
- host firewall rules;
- Docker daemon changes;
- any non-CRM service;
- real data inside the loop.

## Acceptance criteria
- **AC1 / AC2:** unit tests with non-vacuity; gitleaks; digests match the register.

**Operator stage:**
- **AC3:** a bundle built from the accepted commit is reproduced byte for byte, and a tampered bundle is refused.
- **AC4:** deploying to an empty `/srv/CRM/runtime/beta` produces a working `crm-beta`, with no reference to `crm-dev` resources: separate network, volumes and runtime.
- **AC5:** a request from a source that isn't trusted gets 403 at the edge. A request through the PO's HAProxy over HTTPS signs in. `crm-app` (beta) answers only on loopback.
- **AC6:** a backup is taken and restored into the throwaway project, with identical record-count fingerprints.
- **AC7:** `crm-dev` is unaffected: its fingerprints are unchanged before and after.
