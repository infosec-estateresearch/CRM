# CRM-008 — Fixes from the first crm-dev operator load (CRM-003 to CRM-006S)

- **Version:** v1.0, 2026-11-10.
- **Authority:** the PO priority override of 2026-11-10 (Issue #9). These defects block CRM_FUNCTIONAL and BETA_POPULATED.
- **Why:** the PL ran the first operator stage on crm-dev:
  1. back up;
  2. `deploy_custom.sh`, then `provision_access.py`, then CRM-003-F;
  3. `crm-load users`, then `provision_users.py`;
  4. `load.sh dev` on a sealed full selftest.

  The load ended with exit 5, 224 records failed. A diagnostic transport, run by the PL only on crm-dev with synthetic data, read each server rejection reason. The PL then counted, over the real sealed extract, which of these defects affect real data (counts and lengths only).

## Facts verified by the PL (EspoCRM 10.0.12 on crm-dev; real-data figures are counts only)
1. **`ServiceType` has no controller.** `GET/POST ServiceType` returns 404 "Controller 'ServiceType' does not exist", so the importer fails at its index step with `list_failed`.
   - The fix is `custom/Espo/Custom/Controllers/ServiceType.php`, an empty class `ServiceType` extending `\Espo\Core\Templates\Controllers\Base` in the namespace `Espo\Custom\Controllers`.
   - A probe in the dev runtime proved it: list, create and delete all work. No Entity or Repository class is needed.
2. **Currency.** crm-dev Settings have `currencyList ["USD"]` and `defaultCurrency`/`baseCurrency` `USD`, so every Opportunity with an amount is refused with `400 amount validCurrency`. The importer sends `amountCurrency: "GBP"` (mapping `currency`). **37,295 real enquiries have an amount.**
3. **Required owners.** `assignedUser` is `required: true` on core Task, Call and Meeting; it is not required on Account, Contact, Opportunity or Email. A Task whose owner is unresolved is refused with 400. In the real data, every Task and Event owner is a Standard user (4 of them inactive), so every one is exportable. This affects synthetic data only.
4. **Task-Emails with no EmailMessage.** A Task-Email that has no EmailMessage has no `from` address, and `Email.from` is required, so it is refused with 400. **455 of the 34,518 real Task-Emails have no EmailMessage.**
5. **Field length limits** (`maxLength`):
   - Contact `title`: 100;
   - address city, state and country: 100;
   - postal code: 40;
   - Account `name`: 249;
   - `sfStageName`, `sfLeadSource`, `clientReference` and `caseNumber`: 100;
   - ServiceType `name`: 150;
   - phone numbers: 36.

   In the real data, **1 Contact `Title` exceeds 100** and **4 Contact `Phone` values exceed 36**. Every other mapped value fits. Synthetic postal codes reach 42 characters and are refused with `maxLength`.
6. **Email addresses.** Synthetic addresses are refused with `Email to valid`. Every real From/To/Cc/RelationAddress address matches a basic address pattern: 0 invalid; 54 To and 17,293 Cc are blank.
7. **Synthetic Event `Type`** is not in `syntheticEnumMap`, so all 32 synthetic Meetings are refused with `meetingType valid`.
8. **Role `info` key.** `config/access/roles.json` roles carry an `info` key that EspoCRM has no attribute for. Every `provision_access.py` re-run therefore reports `role updated (info)` and sends a PUT, which breaks the CRM-003 rule that a second run makes no changes.
9. **File modes.** `scripts/load.sh`, `scripts/provision_access.py`, `scripts/provision_users.py`, `scripts/check_access.py`, `scripts/crm_api.py` and `load/bin/crm-load.py` have Git mode 100644. The documented `scripts/load.sh …` and `scripts/provision_access.py …` invocations fail with "Permission denied".

## Change
1. **Add the `ServiceType` controller** described in fact 1. Add a unit test: every custom scope with `"entity": true` and `"isCustom": true` has a controller in `custom/Espo/Custom/Controllers/`.
2. **Settings, applied by `provision_access.py`.** For the target, `provision_access.py` sets `currencyList ["GBP"]`, `defaultCurrency "GBP"`, `baseCurrency "GBP"` and `phoneNumberInternational false` through `PUT Settings` as admin, idempotently: it sends only what differs, and a second run reports unchanged. Keep the values in a Git-controlled `config/settings.json`, enforced by the access policy tests. ACCESS.md and IMPORT.md document them.
3. **Required owner.** For Task, Call and Meeting, an unresolved owner refuses the record with the new code `owner_required_unresolved`. The owner is never guessed and no placeholder is used. Account, Contact, Opportunity and Email keep `owner_unresolved` and are still created without an owner.
4. **Task-Email with no EmailMessage.** Import it as a **Task** with the same fields as a plain Task. Its Subject becomes the name, its Description becomes the description, its status and dates are kept, and its parent is kept. It gets the code `task_email_imported_as_task`. Document this.
5. **Over-length values.**
   - Before sending, check each mapped varchar, email and phone value (trimmed) against the target `maxLength`, held in `mapping.json`.
   - If a value is too long, send that attribute as null and record the code `value_too_long`, with the record id and **attribute name** only. Never truncate. Phone numbers longer than 36 become `phone_rejected`.
   - **Raise Contact `title` to 255** in `custom/.../entityDefs/Contact.json` (`maxLength` only), so the real value fits.
6. **Invalid email addresses.**
   - Validate each address the way EspoCRM does (PHP `FILTER_VALIDATE_EMAIL` semantics, approximated conservatively, with tests).
   - An invalid To or Cc address is dropped from the list with `email_address_invalid` (record id only).
   - An invalid or blank `from` on an EmailMessage refuses the record with `email_from_invalid`.
7. **`syntheticEnumMap`** gains Event `Type`, mapped to valid `meetingType` values. It stays selftest-only.
8. **Ignore role `info`.** `provision_access.py` never sends or compares `info`: it is documentation only. Test that a second run against a fake that drops unknown attributes reports unchanged.
9. **Executable bits.** Set Git mode 100755 on the files in fact 9. The test suite asserts this.
