| CRM-D019 | LAN access to the dev CRM (dev only). **Why:** Matt instructed direct access from the two authorised internal networks. This supersedes CRM-001's loopback-only access for dev. **Bind:** `crm-app` publishes 8180 on the host's LAN address only (`CRM_BIND_IP`), never on `0.0.0.0`, and no longer on `127.0.0.1`. The database and the daemon publish nothing. **Enforcement layer:** Apache inside `crm-app`. A read-only, Git-controlled `<Location "/">` holds `AuthMerging And` and `Require ip 127.0.0.1 ::1 ${CRM_ALLOWED_SOURCES}`, so it can only narrow the authorization that already applies. Apache is used because the standing rule rules out host firewalls (no iptables, ufw or nftables, so no `DOCKER-USER` chain). No header is trusted (no `mod_remoteip`). Addresses live only in the runtime env file. **Fail closed:** `scripts/check_access.py dev` refuses bad values (the bind address must be RFC 1918 and inside an allowed network). `scripts/up.sh dev`, `deploy_custom.sh` and `restore.sh` run it before any `up`, refuse any env-file name set in the shell environment, and remove every such name from Compose's environment. A raw `docker compose up` skips the check; Compose refuses an unset or empty variable. Apache does not start if the variable is undefined, and admits loopback only if it is empty. **Residual risks:** plain HTTP on the LAN; every host in the authorised networks reaches the login and admin UI; address-based trust admits a compromised host inside those networks; host-local processes may be admitted. The Apache merge behaviour and source-address preservation are still to be confirmed at the operator stage. **TLS is mandatory before any real data** (CRM-PBI-008). | PROPOSED | Architect directive "CRM-001 authorised LAN access change", on Matt's instruction |

## Product reset: standalone WIP/Revenue proof of concept (2026-11-18)

| ID | Decision | Status | Source |
|---|---|---|---|
| CRM-D035 | **WIP is an independent application; the CRM carries a link only.** The WIP application and its own database are separate, independently versioned and deployed (private WIP repository). The CRM keeps Account, Contact and FirmGroup identity and adds one EspoCRM Account action that navigates to WIP. **Supersedes** the CRM-owned WIP module (CRM-D021, D022, D025, D026, D027 and D031's re-reading of D006) and the **mechanism** of CRM-D033 (read-only JSON API into a CRM panel). CRM-D033's principle, that WIP stays independent and the system of record for WIP data, is **retained**. CRM-PBI-019 to 023 and 025 are superseded; the history, reviews, ledgers and pull requests of the earlier chain are preserved | PROPOSED | PO and CGPT, Issue #81, 2026-11-18 |
| CRM-D036 | **Three identifiers, never confused.** `crmAccountId` (the immutable EspoCRM `Account.id`) is the canonical key for new WIP records and for navigation. `sfId` is the Salesforce id on the Account and is a **legacy join only**, matched exactly. `crmFirmGroupId` is the Account's current CRM group (nullable) and may travel only as non-authoritative interface context; WIP confirms membership by reading the CRM. No fuzzy name matching; no automatic firm creation; WIP's old integer company id is never used as the CRM key | PROPOSED | Issue #81 §3 |
| CRM-D037 | **Integration is browser navigation.** The link carries only the opaque Account id (later, optionally, a group id). No credential, token or financial value appears in a URL. No new JSON endpoint, bearer-token service, CRM-side WIP loader or identity service is built for this milestone | PROPOSED | Issue #81 §2, §4 |
| CRM-D038 | **Data access.** The WIP service reads CRM identity (`account`: id, name, `sf_id`, deleted; later the FirmGroup columns) through its own **read-only, separately credentialed** database login, with parameterised SQL, short timeouts and errors contained inside WIP. The login is new, kept in server-side runtime configuration, and no credential exposed in earlier history is reused. The synthetic proof on `crm-dev` reaches the database by its container network address (no CRM change). **Any longer-lived path** (the recommendation is a loopback-only, per-environment, off-by-default publication of the CRM database port) is a **separate bounded Work Order** and the only thing that would amend CRM-D012 (no published database port); until it is approved, CRM-D012 stands | PROPOSED | Issue #81 §4; architecture record §6 |
| CRM-D039 | **Extension mechanism.** The Account action is a supported EspoCRM customisation: `clientDefs/Account.json` `menu.detail.buttons` item with a `handler` and `actionFunction`, and a browser module under `client/custom/src`. The WIP base URL is a **non-secret runtime parameter** (`wipBaseUrl`) set per environment outside Git. The handler fails closed (warning, no navigation) and makes no network request. No core patch, no PHP, no entity or ACL change. Verified against the installed EspoCRM 10.0.12 client source | PROPOSED | architecture record §5, E7 |
| CRM-D040 | **Client-asset delivery prerequisite.** `main` delivers only `custom/Espo/Custom`; nothing delivers `client/custom/src`. The historical WIP schema, data and import and sync jobs are not changed by the rebuild; a new schema and a reconciled migration are not chosen | PROPOSED | PO clarification (Issue #81); WIP repository record |
